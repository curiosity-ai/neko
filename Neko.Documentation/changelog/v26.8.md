# :icon-sparkles: Features

::: change {badge="New" title="branding.link overrides the navbar brand target"}
The navbar brand — the clickable branding title, and in `blog` mode the logo
wordmark — always pointed at the site homepage (`/index`). Two new
[`branding`](/configuration/core/project#branding) keys make that configurable:
`link` sets the brand's target and `linkTarget` sets its `target` attribute
(`blank`, `self`, `parent`, `top`; a new tab also gets
`rel="noopener noreferrer"`). The link may be an internal path — written with or
without its `.md` / `.html` suffix, which is stripped like any other configured
link — an absolute URL back to a marketing site, or `#` to make the brand inert.
Sub-projects in a multi-repo site inherit `link` and `linkTarget` from the parent
config when they don't define their own, so every sub-site's brand can point at
the shared root. Both default to the previous behaviour when unset.
:::

::: change {badge="New" title="hero supports a third CTA"}
The [`hero`](/components/hero) component took two CTAs — a filled primary
(`cta1`) and an outline secondary (`cta2`). A new `cta3-text` / `cta3-link`
pair adds a third button, in the same outline style as `cta2`, for pages that
split into more than one next step — e.g. a landing page routing readers into
one of two tracks. Omitting it renders exactly as before.
:::

::: change {badge="New" title="neko watch --no-password disables passwords while authoring"}
[Password-protected](/guides/password-protection.md) pages showed their normal
unlock prompt in `neko watch` too, which gets tedious when you're just editing
content and keep hitting it on every reload. `neko watch --no-password` (alias
`--disable-passwords`) ignores both the site-wide `password:` config key and
any page-level `password:` frontmatter for the lifetime of the watch session,
rendering every page in plaintext. It has no effect on `neko build` — a
production build always respects passwords regardless of how the site was
previewed locally. See [Live Editing](/guides/live-editing.md#disabling-password-protection-while-watching).
:::

# :icon-wrench-simple: Improvements

::: change {badge="Changed" title="Live `tesserae` samples now compile with Transpose"}
Live [`tesserae`](/components/tesserae) samples were compiled by
`h5.Compiler.Service`; they are now compiled in-process by
[Transpose](https://www.nuget.org/packages/Transpose.Compiler.Library), the
Roslyn-based C#-to-JavaScript compiler that Tesserae itself moved to. Tesserae
releases from `2026.7` onwards are built for Transpose, so this is what keeps
live samples working against current Tesserae; a `tesserae.version` still pinned
to an H5-era release is now reported as such instead of failing with a wall of
missing-namespace errors. Sample sources that reached into the browser through
the old compiler need two usings renamed — `H5.Core.dom` becomes
`Transpose.Core.dom` and `H5` becomes `Transpose`; everything else is unchanged.

The build also got cheaper. The runtime every sample of one Tesserae version
shares — the Transpose runtime, the Tesserae bundles, its stylesheet and icon
fonts — is now produced once per version and cached, and only each sample's own
code is compiled per sample, in memory. The order those files load in is read
from the page the compiler generates rather than re-derived by Neko, so a change
in the runtime's layout no longer needs a matching change here. Cached samples
from an earlier Neko are ignored (the cache format was bumped), so the first
build after upgrading recompiles every sample once.

Dropping H5 also drops three dependencies Neko only carried for it:
`h5.Compiler.Service`, the `ZLogger` 1.x pin it needed at runtime, and
`Microsoft.Build.Locator` — the CLI no longer registers an MSBuild instance on
startup, because Transpose reads project files directly.
:::

# :icon-bug: Fixes

::: change {badge="Fixed" title="Search was unreachable on mobile"}
The documentation header's action row — the wide `Search ⌘K` box, the recent-pages
clock, and the theme toggle — is hidden below the `md` breakpoint, so on a phone
the search box simply disappeared. With no keyboard there was no `⌘K` fallback
either, leaving search unreachable on mobile entirely. The header now renders a
compact search icon (`#mobile-search-btn`) at its right edge, visible **only**
below `md`, which opens the same search modal. The desktop header is unchanged:
the icon is hidden from `md` up, so the two triggers never show together.

The modal itself was also tuned for small screens: it keeps side padding instead
of running edge-to-edge (which clipped its rounded corners), sits a little higher
on the page, caps its result list at `60vh` so results stay scrollable above the
on-screen keyboard, and hides the `↑ ↓ / ↵` keyboard-hint footer, which is dead
space on touch. From `sm` up it renders exactly as before. `blog` mode is
untouched — there search lives in the page content on every viewport.
:::

::: change {badge="Fixed" title="Icons (and other assets) 404 on sub-project pages in multi-repo watch"}
The UIcons stylesheets, the emoji stylesheet, and several `<head>`/auxiliary
scripts (search, history, the force-directed graph, syntax-highlighting themes,
and the password-unlock script) were linked from the domain root (`/assets/…`)
instead of each (sub-)site's own route prefix — unlike `tailwind.css`, which
already got this right. A sub-project page in a multi-repo `neko watch` (or any
deployment nesting projects under one domain) would then request the *root*
project's copy of these assets instead of its own, 404ing — and silently
leaving icons unrendered — whenever no root project happened to share that
path. All of these now resolve under the page's own prefix, exactly like
`tailwind.css`.
:::

::: change {badge="Fixed" title="Build broke from two overlapping `neko watch --no-password` implementations"}
Two PRs landed the same feature independently within minutes of each other:
one added a `NekoConfig.DisablePassword` runtime flag checked at render time,
the other cleared `password` config/frontmatter directly during parsing and
renamed the `SiteBuilder` constructor parameter in the process. The second PR
merged `main` first but didn't reconcile the two — leaving a `SiteBuilder`
constructor that referenced a parameter name which no longer existed (`error
CS0103`) alongside dead `DisablePassword` checks in `HtmlGenerator.Content.cs`,
`HtmlGenerator.Sidebar.cs`, and `SiteBuilder.cs`'s sitemap/search-index
protected-page checks that could never fire. Removed the unused flag, property,
and checks, keeping the single working implementation (config/frontmatter
clearing) that the merged docs and tests already describe.
:::
